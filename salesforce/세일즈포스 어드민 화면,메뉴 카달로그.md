
# DIO CRM Admin Screen/Menu Catalog v1.0

## 1. 설계 목적

DIO CRM의 관리자 기능은 Salesforce 관리자 기능을 그대로 복제하는 것이 아니라 다음 범위까지 내재화한다.

**관리자가 직접 변경하는 영역**

운영조직 / 사용자 / 권한 / 데이터 접근범위 / 화면 표시 / 공통코드 / 상태값 / 데이터 Import·Export / 감사로그 / ERP·API 연계상태 / Batch 운영

**개발자가 관리하는 영역**

DB Entity 생성 / DB Column 생성·변경 / 데이터 타입 변경 / Formula Engine / Lookup 관계 생성 / 임의 Business Logic / API 프로그램 변경

핵심 구조는 다음과 같다.

`Admin UI → Admin API → Metadata/Config → CRM Web·Mobile → Business API Validation → Audit`

화면만 Metadata를 적용하는 것이 아니라 **API도 동일한 설정을 사용해야 한다.**

# 4. ADM-SCR-000 관리자 HOME

## 목적

관리자가 CRM 운영상태를 한 화면에서 파악하고 문제가 있는 관리영역으로 바로 이동한다.

### Field / Widget

| Field | 설명 |
|---|---|
| Active User | 활성 사용자 |
| Disabled User | 비활성 사용자 |
| Unassigned Lead | 담당자가 없는 Lead |
| Import Error | 최근 Import 오류 |
| Interface Error | ERP/API 오류 |
| Batch Failure | Batch 실패 |
| Failed Login | 인증 실패 |
| Config Change | 최근 관리자 설정 변경 |
| Pending Retry | 재처리 대기 |
| Last ERP Sync | 최근 ERP 연계시간 |

### Action

`사용자 관리 / Interface 오류 / Batch 오류 / Audit Log / Import 오류` 바로가기.

### Rule

오류 Count는 관리자가 접근 가능한 영역만 표시한다.

### Permission

`CRM_ADMIN / SYSTEM_ADMIN / INTERFACE_ADMIN`

### API

```text
GET /api/admin/dashboard
GET /api/admin/dashboard/alerts
```

### Metadata

```text
ADM_DASHBOARD_WIDGET
ADM_DASHBOARD_PREF
```

# 5. 사용자 / 조직

## ADM-SCR-101 사용자 관리

### Field

| Field | 설명 |
|---|---|
| user_id | CRM User ID |
| emp_no | ERP 사번 |
| user_name | 사용자명 |
| login_id | 로그인 ID |
| org_code | 조직 |
| position | 직급 |
| role | CRM Role |
| data_scope | 데이터 접근범위 |
| status | Active / Disabled |
| last_login_at | 최근 로그인 |
| source | ERP / Manual |

### Search

이름 / 사번 / 조직 / Role / 활성상태.

### Action

`신규 / 수정 / 활성화 / 비활성화 / Role 변경 / 비밀번호·인증상태 확인 / 데이터 이관`

### Business Rule

ERP에서 전달되는 `사번·성명·조직·직급`은 CRM에서 임의 변경하지 않는다.

CRM 관리자는 CRM Role, Data Scope, 추가권한을 관리한다.

퇴직자는 삭제하지 않고 `Disabled` 처리한다.

### Permission

`CRM_ADMIN`

### API

```text
GET    /api/admin/users
GET    /api/admin/users/{userId}
POST   /api/admin/users
PATCH  /api/admin/users/{userId}
POST   /api/admin/users/{userId}/enable
POST   /api/admin/users/{userId}/disable
```

### DB

```text
ADM_USER
ADM_USER_ORG
ADM_USER_ROLE
ADM_USER_PERMISSION
```

# 38. 공통 관리자 권한

관리자라고 모두 같은 권한을 주지 않는다.

| 관리자 Role | 주요 권한 |
|---|---|
| SYSTEM_ADMIN | 전체 |
| CRM_ADMIN | 사용자·조직·권한·화면·코드 |
| DATA_ADMIN | Import / Export / 대량처리 |
| INTERFACE_ADMIN | ERP/API/Batch |
| SECURITY_ADMIN | 인증·접근·Audit |
| AUDITOR | 모든 Audit 조회, 수정 불가 |

특히 `AUDITOR`는 조회 전용으로 한다.

---

# 39. 권한 계산 기준

최종 권한은 다음 구조로 계산한다.

```text
최종 권한

= Role Permission
+ User Additional Permission
+ Data Scope
+ Record Share
- Security Restriction
```

Security Restriction이 최우선이다.


```text
[Master / Detail]

│
│     우측 상세
│
│     기본정보
│     설정
│     권한
│
```

```text
[Matrix]

Role × Permission
```

```text
[Tree]

조직
 └─ 부서
     └─ 팀
```

```text
[Wizard]

파일
 → Mapping
 → Validation
 → Preview
 → Execute
 → Result
```

이 5개 Pattern으로 대부분의 관리자 화면을 구성할 수 있다.

### P5 — Audit / Interface

### P6 — System

`ADM-SCR-801~803`

# 48. 목업 개발 완료 기준

Admin Mockup을 완료했다고 판단하려면 최소한 다음 Flow가 실제 화면에서 연결되어야 한다.

```text
사용자 선택
 → Role 변경
 → 권한 Matrix 확인
 → Data Scope 지정

Lead 화면 선택
 → Field 표시/숨김 변경
 → 필수 여부 변경
 → Layout 변경

Lead Status
 → 코드 추가
 → 상태전이 설정

Excel Import
 → Mapping
 → Validation
 → Preview
 → 결과확인

ERP Interface
 → 오류조회
 → 오류상세
 → 재처리

Audit
 → 관리자 변경내용 확인
```

이 Flow가 동작하면 관리자 기능에 대한 **UX/기능 검증을 먼저 수행하고 DB/API 구현 단계로 넘어갈 수 있다.**
