# ADR 0004. 하위 호환: 지우지 않고 폐기 예정으로 표시한다

## 상태

채택 (2026-11-26, F0-4). 설정 형식(`FieldDef` 의 폐기 예정·별칭)과 검사 함수(`diffBundles`)는 F1-1 에서 생겼다. 가드 연결은 F1-2 에서 생겼다(보호 검사 P6).

## 맥락

설정으로 개체와 필드를 만들면, 그 이름은 저장된 데이터, 목록 설정, 승인 규칙, 보고서, 연동에서 다시 쓰인다.
AI 는 "안 쓰는 것 같다"는 이유로 필드를 지우거나 이름을 바꾼다. 그러면 그 이름을 쓰던 다른 설정과 이미 저장된 데이터가 조용히 깨진다.
법인마다 게시 시점이 달라서, 한 법인에서는 안 쓰는 필드를 다른 법인은 쓰고 있을 수 있다.

## 결정

1. 게시된 개체와 필드는 지우지 않는다. 더 쓰지 않을 것은 "폐기 예정"으로 표시한다.
   폐기 예정인 것은 새로 쓰는 화면에서 숨기지만, 저장된 값과 그것을 읽는 기존 설정은 그대로 동작한다.
2. 이름을 바꿀 때는 옛 이름을 별칭으로 남긴다. 옛 이름으로 들어온 요청과 저장된 데이터는 새 이름으로 읽힌다.
3. 실제 삭제는 따로 승인받는 작업이다. 쓰는 곳이 없다는 증거(ADR 0005)를 붙이고 사람이 승인한다.
4. 필드의 종류를 바꾸는 것(예: 글자에서 숫자로)은 이름 변경이 아니라 새 필드를 만들고 옛 필드를 폐기 예정으로 두는 일이다.
5. 아직 한 번도 게시하지 않은 초안 안에서는 자유롭게 지우고 바꿀 수 있다.

## 결과

- 좋은 점: 설정을 바꿔도 이미 돌아가는 화면과 저장된 데이터가 깨지지 않는다.
- 치르는 값: 폐기 예정 항목이 쌓인다. 주기적으로 3번 절차로 정리해야 한다.
- 지금 있는 것: admin 계약의 확장 필드에는 `active` 값이 있다(`packages/contracts/src/admin/schemas.ts`).
  `active` 를 끄면 그 필드에 쓰는 요청은 `EXTENSION_INACTIVE` 로 거절된다(`packages/contracts/src/admin/security.ts`).
  이것은 "끄기"이지 이 ADR 의 "폐기 예정 표시"와 "별칭"은 아니다. 폐기 예정 표시와 별칭은 메타모델(ADR 0006)의 `FieldDef`·`ObjectDef` 에 있다.

## 덧붙임 (2026-11-28, F2-4): 저장된 데이터가 이름 바꾸기를 따라가는 법

결정 2 의 "저장된 데이터는 새 이름으로 읽힌다"를 자동 API(F2-4)의 표에서 이렇게 지킨다.

- 표와 열의 실제 이름은 처음 만들 때 한 번 정하고 `dbo.crm_meta_obj_name` 표에 적어 둔다(개체 키 → 표, 필드 키 → 열).
  처음 이름은 `crm_obj_<개체 키>`, `f_<필드 키>` 다.
- 개체나 필드의 이름을 바꾸고 옛 이름을 별칭으로 남겨 게시하면, 엔진은 새 이름이 적혀 있지 않을 때 별칭으로 적힌 줄을 찾아 **같은 표·같은 열**을 쓴다.
  새 표나 빈 열을 만들지 않는다. 그리고 새 이름도 같은 열로 적어 둔다.
- 적힌 줄은 지우지 않는다. 나중에 별칭을 지워도 새 이름은 계속 같은 열을 읽는다(새 이름이 게시할 때 같은 열로 적히기 때문이다).
- **게시본에서 사라진 이름은 은퇴한다(2026-11-28 고침).** 게시하거나 rollback 할 때마다, 같은 트랜잭션에서, 새 게시본에 키로도 별칭으로도 없는 이름의 줄에 은퇴 표시(`retired`)를 한다(`crm-obj-name-sync.ts`).
  은퇴한 이름은 다시 따라가지 않는다. 나중에 같은 이름(또는 그 이름을 별칭으로 가진 것)의 개체·필드가 생기면 **새 표·새 열**(`crm_obj_<키>_r2`, `f_<키>_r2` …)을 받는다.
  이미 있는 표나 열을, 살아 있는 줄이 없는 이름에 주는 일은 없다(적힌 적 없는 표·열도 마찬가지다).
  이유: 개체나 필드를 폐기 예정 → 삭제한 뒤 같은 이름으로 다시 만들면 설정 비교는 "새 것"으로 보는데, 옛 표를 다시 쓰면 옛 행이 새 행 권한(예: 전체 공개)으로 보이게 된다.
- 옛 게시본을 들고 있던 요청은 표를 만들지도, 이름을 적지도, 행을 쓰지도 못한다. 표 만들기와 생성·수정은 자기 트랜잭션 안에서 게시 포인터를 잠그고(게시가 먼저 잡는 잠금과 같은 줄)
  "내가 읽은 게시본과 도장이 지금도 그대로인가"를 확인한다. 아니면 503 `PUBLISHED_METADATA_CHANGED` 로 끝나고 아무것도 바뀌지 않는다.
  표 만들기는 그 개체와 필드가 지금 게시본에 정말 있는지도 확인한다. 그래서 은퇴한 이름이 늦게 도착한 요청 때문에 되살아나지 않는다.
- 치르는 값: 삭제를 게시한 뒤에는 rollback 으로 그 개체·필드가 있던 게시본으로 돌아가도 **옛 데이터가 보이지 않는다**(빈 새 표·새 열). 옛 표와 열은 지워지지 않고 그대로 남는다.
  옛 데이터를 다시 잇는 것은 사람이 하는 마이그레이션이고(결정 3 의 "따로 승인받는 작업"), 게시만으로는 할 수 없다. 그 절차는 아직 없다.
- 이름 하나가 표 둘 또는 열 둘을 가리키는 개체·필드(합치기)는 게시가 멈춘다(`CRM_OBJ_TABLE_AMBIGUOUS`, `CRM_OBJ_COLUMN_AMBIGUOUS`. 필드는 설정 비교의 D06 이 먼저 막는다).
  이름을 찾는 순서(키, 그다음 별칭)는 설정 비교와 저장소가 한 함수(`resolveByNames`)를 쓴다.
- 행 권한의 담당자 필드 이름을 별칭을 남기고 바꾸는 것은 같은 필드이므로 넓히기(D05)가 아니다. 단, 지금 설정의 필드 하나가 기준의 필드 정확히 하나를 이을 때만이다(`diff-access.ts` 의 `continuedField`).
- 코드: `backend/src/database/crm-obj-name-map.ts`, `crm-obj-name-sync.ts`. 검사: `crm-obj-name-map.spec.ts`, `engine-compat.spec.ts`, `engine-retired-names.spec.ts`(합성, SQLite 가짜 DB). 실제 SQL Server 에서는 확인하지 않았다.

## 기계 검사

- 검사 함수가 있다(F1-1, ADR 0006): `packages/contracts/src/metadata/diff.ts` 의 `diffBundles(base, head)`.
  폐기 예정 표시 없이 사라진 개체·필드·목록 보기·동작·메뉴(D01), 별칭 없는 이름 바꾸기(D02), 허용 표(`SAFE_TYPE_WIDENINGS`) 밖의 종류 바꾸기(D03)를 오류로 낸다.
  폐기 예정 필드를 새로 쓰기 시작하면 경고(D04)다. 폐기 예정 표시(`deprecated`)와 별칭(`aliases`)은 `FieldDef`·`ObjectDef` 에 있다.
- 보호 검사 P6 `metadata-compat`(F1-2): `--protect` 가 기준 브랜치의 `metadata/` 와 지금의 `metadata/` 를 `diffBundles` 로 비교하고, 오류가 있으면 실패한다. 행 권한 넓히기(D05)만 규칙 하나씩 예외로 선언할 수 있다(ADR 0007). 이 ADR 의 대상인 D01~D03 과 읽지 못하는 설정은 예외로 선언할 수 없다.
  보호 검사는 PR 과 `pnpm crm verify` 에서만 돈다. `pnpm crm check` 는 기준 브랜치와 비교하지 않는다.
