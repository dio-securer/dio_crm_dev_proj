# 본사 CRM 표준 프로세스·화면 목업 단계별 작업지시서

작성일: 2026-10-22 · 상태: 실행 지시 기준 · 선행 문서: [작업설계서](01_HQ_CRM_Mock_Work_Design.md)

## 1. 실행 범위와 공통 규칙

목표는 현재 사용되는 HQ 화면 전체의 목록·상세·탭·팝업·입력·저장·조회·상태 전이를 구현하고, 하나의 목업 데이터셋에서 ERP 연동을 포함한 업무를 끝까지 조작할 수 있게 하는 것이다. H00부터 H07까지 순서대로 수행한다. 각 단계의 완료 조건을 충족하지 못한 채 다음 단계의 완료를 선언하지 않는다. 법인별 사용/미사용을 편집하는 관리자 UI는 이 작업 이후의 범위지만, 본사 설정 해석·미리보기·검증은 H07에서 확인한다.

기준 입력은 [P0 화면·메뉴 카탈로그](../../spec/screens/P0-08_screen_menu_catalog.md), 현재 [HQ 14개 화면 진입점](../../frontend/src/market/templates/hq/hq-screen-manifest.ts), [화면 등록부](../../frontend/src/app/screen-registry.tsx), [경로 목록](../../frontend/src/app/route-config.ts) 및 작업설계서 §2의 7개 교육 문서다. `1차`와 `02·03`, `05`와 `06·07`의 중복 구간을 별도 요구로 세지 않는다. 영상의 교육 슬라이드, 탭, 팝업을 독립 메뉴로 자동 등록하지 않는다.

모든 단계에서 다음을 지킨다.

1. 시작 시 브랜치·커밋·미커밋 파일을 기록한다. 기존 사용자 변경을 덮어쓰지 않는다. 이 문서 작성 시점의 `backend/src/config/env.ts` 변경과 `salesforce/` 미추적 폴더는 본 작업의 결과가 아니다.
2. 기존 HQ 화면·업무 규칙과 GLOBAL 프로필을 회귀 기준으로 유지한다. 기존 DB 마이그레이션과 시드를 소급 수정하지 않는다. 새 영속 구조가 필요하면 새 버전으로 추가한다.
3. 등록부의 안정 ID를 화면·API·문서에서 공유한다. 배열 순서나 화면 라벨을 참조 키로 쓰지 않는다. 등록되지 않은 경로·필드·액션·프로세스 전이는 거부한다.
4. 화면 표시 조건과 서버 실행 조건을 같은 정책으로 평가한다. 메뉴/버튼 숨김만으로 권한·업무 제한을 구현하지 않는다.
5. 교육 문서의 근거 상태를 `시연 확인`, `교육자료 설명`, `기존 코드`, `설계 가정`, `미확인`으로 기록한다. 자료에 없는 세부 규칙은 기존 코드·업무 명세를 먼저 확인하고, 그래도 비어 있으면 현재 화면의 업무를 끝까지 수행할 수 있는 목업 규칙을 정해 구현한다. 가정은 실제 본사 정책과 구분한다.
6. ERP가 연동된 환경을 기본 업무 조건으로 둔다. 목업 실행에서는 [P0 인터페이스 카탈로그](../../spec/interfaces/P0-07_interface_catalog.md)의 요청·결과 계약을 따르는 ERP 어댑터가 거래처·계약 승인, 품목·단가·재고, 주문·납품, 매출·수금·반품 결과를 반환한다. 기본 시나리오는 성공이며 실패·지연·재처리도 선택할 수 있다. 목업 결과에는 `MOCK`를 표시하고 실제 ERP 접속 여부는 별도 검증 결과로 구분한다.
7. 단계마다 변경 파일, 기준 커밋, 실행 명령과 결과, 실패/미실행 사유, 카탈로그 ID 및 시나리오별 증거를 `docs/hq-standard/implementation/Hxx-report.md`에 남긴다. 로그·화면 캡처는 `docs/hq-standard/implementation/evidence/`에 저장한다.

기본 검증 명령은 `pnpm build`, `pnpm test`, `pnpm regression:multi-market`, `pnpm i18n:check`, `pnpm pwa:check`다. 업무 단계의 실제 브라우저·HTTP 인수 명령은 H02에서 별도 스크립트로 등록한다. 문서에 PASS라고 쓰려면 해당 코드 기준에서 명령을 실행하고 종료 상태·대상 데이터셋·로그를 기록한다. 문서만 작성한 단계에는 불필요한 전체 회귀를 반복하지 않는다.

## 3. H00 — 기존 화면·업무 기준 대조

### 입력과 조사

1. `git status --short --branch`와 현재 커밋을 기록한다. 현재 파일을 수정하지 않은 상태에서 `pnpm build`, `pnpm test`, `pnpm regression:multi-market`의 기준 결과를 확보한다. 환경 문제로 실패하면 원인과 기존/신규 여부를 분리한다.
2. P0 카탈로그의 `SCR-*` 34개를 한 행씩 옮기고, 현재 라우트·화면 등록부·관리자 화면에서 실제 사용되지만 카탈로그에 없는 화면을 추가 행으로 등록한다. 각 행에 실제 경로, `HQ_*` screen key, 컴포넌트, 목록·상세·탭·팝업 구분, API, 저장소, 권한, 모바일 동작을 채운다. 14개 HQ 화면 진입점과 대응하지 않는 ID도 삭제하지 않는다.
3. 교육 문서의 S01–S22, S41–S51, S501–S527을 카탈로그 행·화면 내부 영역·액션에 연결한다. `02·03`, `06·07`의 반복 ID는 같은 영상 구간에 연결하고, 교육 슬라이드는 업무 규칙 근거로만 연결한다.
4. 필드별 `fieldKey`, 라벨, 표시 화면/섹션, 입력·표시 형식, 별표 관찰, 실제 필수 규칙, 기본값, 선택지 원천, 읽기/쓰기 권한, ERP/심평원 원천 여부, 계산/상태 의존성, 근거 상태를 수집한다. 문서의 미확인 속성은 빈칸 대신 `미확인`으로 적는다.
5. 버튼/이벤트별 시작 상태, 입력, 성공·실패 응답, 다음 상태와 화면, 기존 API를 수집한다. [P0 인터페이스 카탈로그](../../spec/interfaces/P0-07_interface_catalog.md)의 `IF-ERP-001`–`014` 및 `IF-HIRA-001`을 관련 화면·데이터·결과 상태에 배치한다. 별도 데이터셋의 계약 00058196/00058077/00045297 등은 서로 다른 사례로 기록한다.
6. 각 카탈로그 행을 `충족`, `부분`, `미구현`, `규칙 확인 필요`로 판정하고 근거를 남긴다. 이는 작업량 구분이며 어느 행도 최종 범위에서 제외하지 않는다. 관리자 화면 5개와 Drive 문서 밖의 활동·직출직퇴·운영 화면은 기존 명세·코드 기준을 병기한다.

### 산출물과 종료 조건

`implementation/H00-coverage.md`에는 34개 카탈로그 행 전부와 추가 사용 화면, 14개 HQ 진입점·교육 분석 ID·현재 사용 동작의 대응을 넣는다. `implementation/H00-fields.md`에는 화면별 필드·액션·ERP 인터페이스 목록과 미확인 속성을 넣는다. `implementation/H00-report.md`에는 기준 커밋과 테스트, 기존 기능 보존 목록, H01–H07의 실측 작업량·파일 후보를 기록한다. `SCR-*` ID 누락 0건, 사용 중인 화면의 미등록 0건, ERP 인터페이스의 화면/결과 대응 누락 0건, 출처 없는 필수/권한 확정 0건, 교육 슬라이드를 메뉴로 잘못 등록한 건수 0건일 때 H00을 완료한다.

## 4. H01 — 본사 표준 등록부와 검증 계약

### 구현 지시

1. `packages/contracts/src/`에 HQ 표준의 타입·검증기를 둔다. `Process`, `Screen`, `MenuNode`, `Tab`, `Section`, `Field`, `Action`, `Transition`, `Evidence`를 안정 ID로 참조하고, 실제 화면/액션 목록은 H00 대응표에서 채운다. 기존 `globalization` 계약과 화면 키를 임의 변경하지 않는다.
2. `frontend/src/app/`의 현재 14개 화면 컴포넌트 등록을 재사용한다. 표준 `screenKey`가 등록되지 않은 화면, 동일 route, 부모 없는 메뉴, 메뉴 순환, 존재하지 않는 필드·액션·프로세스 참조를 등록부 검사에서 거부한다.
3. 프로세스 전이와 화면 표시를 분리한다. 한 화면을 여러 프로세스가 사용할 수 있으며, 메뉴 노출은 활성 프로세스가 하나 이상이고 화면·권한·기능 조건이 맞을 때만 허용한다. 공유 화면에서도 특정 프로세스의 액션은 그 프로세스 조건을 별도로 확인한다.
4. 필드에 `observedRequired`와 실행용 `requiredRule`을 분리한다. `locked/overridePolicy`, 값 원천, 마스킹·읽기/쓰기 권한, 숨김 시 대체값을 표현한다. 필수 필드를 숨기거나 상태 전이에 필요한 필드를 제거하는 설정은 검증 실패로 만든다.
5. HQ 기본 버전과 출처를 넣는다. 이후 법인 override는 안정 ID를 대상으로만 허용하며 상위 버전 변경 시 검증·재적용할 수 있게 버전 참조를 준비한다. 이 단계에서 법인 편집 UI는 만들지 않는다.

### 수정 대상과 검증

주요 수정 대상은 `packages/contracts/src/`, `frontend/src/app/`, 필요한 경우 `backend/src/globalization/`이다. H00에서 확인한 필드 프로필·기능 프로필을 재사용한다. 단위 검증은 중복 ID, 미등록 키, 메뉴 순환, 잘못된 부모, 필수 필드 숨김, 잠금 완화, 공유 화면/프로세스 조건을 실제 HQ 등록부로 실행한다. 34개 카탈로그 행의 대응 키와 14개 화면 진입점에 미해결 참조가 없고 기존 HQ/GLOBAL 화면 테스트가 유지될 때 완료한다.

## 5. H02 — 격리된 HQ 목업 실행 기반

### 구현 지시

1. `datasetId`, `schemaVersion`, 안정 업무 ID, 목업 실행 모드를 정의한다. 시드의 리드·거래처·연락처·활동·기회·계약·수금계획·주문·ERP 결과가 서로 같은 참조 ID를 사용하게 한다. 기본 시드는 ERP 거래처·계약 승인과 주문 결과까지 정상으로 진행할 수 있어야 한다.
2. `backend/src/modules/`의 기존 업무 서비스·규칙에 필요한 저장소 경계를 먼저 확인한다. 실제 DB 연결 경로를 변경하지 않고 격리된 목업 저장소를 붙인다. 프런트의 `frontend/src/demo/`에 이미 있는 별도 localStorage 샘플과 HQ 목업을 혼합하지 않는다. 목업에서도 기존 API의 요청·응답·오류 형태를 유지한다.
3. 시드에는 ERP 승인으로 이어지는 거래처·계약·주문, 미승인 거래처, 중복 후보, 실패·지연 연동, 소유자가 다른 리드, 승인 대기 보고, 미수 회차, 재고 0/음수·주문불가 품목, 좌표 없는 주소를 포함한다. 영상의 서로 다른 거래를 하나의 연속 사례로 합치지 않는다.
4. 명시적 초기화 API와 화면을 만들고 초기화 전 영향 범위를 표시한다. 목업 데이터를 초기화해도 운영 DB와 GLOBAL 데모의 저장값은 바뀌지 않아야 한다. 새로고침·서버 재시작 때 유지할 범위는 실행 모드의 저장 수명으로 명시한다.
5. P0의 `IF-ERP-001`–`014`와 `IF-HIRA-001`별 요청·결과 DTO, 업무 키, 멱등 키, 원천 시스템, 상태 변경, 인터페이스 로그를 정의한다. 목업 ERP 어댑터는 정상 응답을 기본으로 하고 실패·지연·중복·역순 결과와 사용자 재처리를 결정적으로 재현한다. 거래처 승인 결과는 수주 조건, 계약 승인 결과는 주문 조건, 품목 조회는 주문 가능/단가/재고, 주문·납품·매출·수금 결과는 관련 목록과 원장에 반영한다.
6. 실제 ERP가 연결되는 실행 모드는 같은 DTO와 업무 상태 반영기를 사용하도록 어댑터 경계를 둔다. 실제 주소·인증·payload가 제공되지 않은 상태에서 실접속 성공을 주장하지 않는다. 목업 모드에서는 실제 ERP·심평원·메일·지도 송신을 차단하고 `MOCK` 표시를 유지한다. 인증/권한 실패는 화면 숨김과 별개로 API에서 반환한다.
6. `package.json`에 HQ 목업 실행 및 관련 검증 명령을 등록하고 테스트 데이터 초기화 절차를 `implementation/H02-report.md`에 적는다.

### 완료 조건
