# 본사 CRM 표준 프로세스·화면 목업 구현 작업설계서

작성일: 2026-10-22 · 상태: 구현 전 작업설계 · 대상 저장소: `dio_crm_dev_proj`

실행 순서와 단계별 완료 조건: [단계별 작업지시서](02_HQ_CRM_Mock_Implementation_Instructions.md)

## 1. 목표와 완료 상태

본사(HQ)의 프로세스, 메뉴, 화면, 화면 항목과 동작을 하나의 표준 등록부로 정의한다. 기존 본사 화면과 API를 재사용하면서 현재 사용되는 화면의 목록·상세·탭·팝업·입력·저장·조회·상태 변화를 모두 동작하도록 완성한다. 사용자는 목업 데이터로 리드부터 거래처·기회·계약·수금계획·주문·ERP 결과·납품·매출·수금 조회까지 이어지는 흐름과 활동·승인 흐름을 실제 화면에서 조작할 수 있어야 한다. 각 화면은 같은 표준 등록부에서 제목·탭·섹션·항목·액션을 읽고, 다음 화면에는 앞 화면에서 저장한 값과 상태가 나타나야 한다.

이 작업의 산출물은 **현재 사용되는 본사 화면 전체와 ERP 연동이 동작하는 실행 가능한 목업**이다. ERP가 연결된 환경을 기본 업무 조건으로 두고 거래처 등록·승인, 계약 등록·승인, 품목·단가·재고 조회, 주문·납품, 매출·수금·반품 결과와 실패·재처리까지 화면과 데이터에 반영한다. 목업 실행에서는 동일한 인터페이스 계약을 사용하는 ERP 어댑터가 결과를 생성한다. 실제 ERP 접속 검증은 제공된 접속 정보와 환경에서 별도로 수행한다. 법인별 사용/미사용 편집기는 다음 단계로 두되 등록부의 안정 ID, 상속 가능 항목, 게시 버전, 참조 무결성은 이번 단계에 정의한다.

완료 판정은 화면 수가 아니라 다음 네 가지로 한다.

1. [기존 화면·메뉴 카탈로그](../../spec/screens/P0-08_screen_menu_catalog.md)의 34개 화면 ID와 현재 라우트·화면 등록부에서 추가로 확인된 사용 화면 모두가 구현 화면 또는 명시된 화면 내 영역·대화상자에 대응하고 현재 사용되는 조작을 수행한다. 목록·상세·탭·팝업의 열기/닫기, 조회·입력·검증·저장·오류·다음 화면 연결을 확인한다.
2. 14개 [본사 화면 진입점](../../frontend/src/market/templates/hq/hq-screen-manifest.ts)의 경로와 메뉴가 등록부를 통해 해석된다. 열 수 없는 화면은 메뉴에 노출되지 않으며 직접 URL/API 접근도 같은 사용·권한 규칙을 따른다.
3. 본 문서 §7의 목업 시나리오가 서로 연결된 동일 데이터셋에서 통과한다. 기본 시나리오는 ERP 등록·승인과 결과 수신까지 성공하며 요청 성공과 외부 처리 완료를 각각 다른 상태로 기록한다.
4. 화면·항목·동작별 출처와 검증 상태를 추적한다. 자료에 없는 상세 규칙은 현재 코드·기존 업무 명세를 먼저 확인하고, 여전히 비어 있으면 동작 가능한 목업 규칙을 명시하여 구현한다. 미확인 규칙을 확정된 운영 정책으로 표현하지 않는다.

## 3. 본사 표준 모델

표준 등록부는 아래 관계를 안정 ID로 표현한다.

```text
Process ──(uses)──> Screen ──(contains)──> Tab/Section/Field/Action
   │                    │
   ├── Transition       ├── Route
   └── Dependency       └── MenuNode ──> Permission
```

| 계약 | 필수 값 | 해석 규칙 |
|---|---|---|
| Process | `processKey`, 이름·순서, 시작/종료 상태, `screenKeys`, 전이, 선행조건 | 한 화면을 여러 프로세스에서 참조할 수 있다. 프로세스의 상태 전이는 메뉴 클릭과 별개다. |
| Screen | `screenKey`, `routeKey`, 화면 유형, 지원 장치, `tabKeys`, `actionKeys` | `screenKey`는 실제 렌더러에 등록되어야 한다. 상세·팝업·하위 영역은 부모 화면을 명시한다. |
| MenuNode | `menuKey`, 부모, 순서, `screenKey`, 필요한 권한 | 메뉴는 화면의 진입점이다. 탭/팝업을 자동으로 독립 메뉴로 만들지 않는다. |
| Field | `fieldKey`, 엔티티·섹션, 라벨 키, UI 형식, 값 형식, 표시·필수·읽기 전용, 선택지 원천, 기본값, 검증, 데이터 원천 | 필드 사용 여부와 값 저장 여부를 구별한다. ERP/심평원 원천값을 숨겨도 원본 레코드는 지우지 않는다. |
| Action | `actionKey`, 입력, 권한, 사용 조건, 상태 전이, 결과·오류 | UI와 서버/목업 엔진이 같은 조건을 평가한다. 버튼을 감추는 것만으로 실행을 막지 않는다. |
| Evidence | 출처 URL/파일·분석 ID, 근거 상태, 미확인 항목 | 가정은 정책 확정값과 구분하여 검토·변경할 수 있게 한다. |

본사 프로필의 기본값은 모든 등록 화면·항목을 무조건 켜는 값이 아니다. 업무 선행조건과 권한을 가진 사용자가 이용할 수 있는 화면을 명시한다. 이후 법인 설정은 등록된 키의 허용된 속성만 덮어쓴다. 필수 업무 단계, 참조 중인 화면, ERP 원천값, 법정·감사 항목은 마음대로 숨기거나 완화할 수 없도록 `locked` 또는 `overridePolicy`를 정의한다. 본사 게시본의 ID와 법인 적용본의 부모 버전을 보존하며, 상위 변경은 법인에 자동 반영하지 않고 검증 후 적용한다.

메뉴 표시 조건은 `해당 화면을 사용하는 활성 프로세스가 하나 이상 있음 ∧ 화면 사용 ∧ 등록된 경로 ∧ 사용자 권한 ∧ 기능 선행조건`으로 정의한다. 한 화면이 여러 프로세스에 속할 때 화면 진입은 허용되더라도 해당 프로세스의 전이·액션은 별도로 검사한다. 필드 표시 조건은 `화면 항목 사용 ∧ 업무 조건 ∧ 읽기 권한`이며 수정 조건은 별도의 쓰기 권한과 상태 잠금을 더한다. 필수 필드를 숨기려면 기본값·대체 입력·업무 단계 제외 중 하나가 검증되어야 한다. 불가능하면 게시를 거부한다.

현재 화면의 존재는 상세 속성과 상호작용의 완료를 의미하지 않는다. 착수 시 34개 카탈로그 ID와 현재 라우트·등록부에서 발견한 추가 사용 화면 각각을 `충족`, `부분`, `미구현`, `규칙 확인 필요`로 판정하고 UI 경로·컴포넌트·API·데이터 필드를 기록한다. 이는 작업량 분류이며 최종 인수 때는 모든 화면이 `동작 확인`이어야 한다.

카탈로그에서 메뉴는 홈, 리드, 거래처, 기회, 활동, 활동보고/승인, 계약/수금, 주문/납품, 원장/명세서, 분석, 관리자의 상위 그룹으로 시작한다. 실제 사이드 메뉴는 사용자 역할에 맞게 필터링한다. `Service`, `Sales`, `Order`, `History`, `병원현황`, `현황분석` 같은 거래처 탭과 주문 대화상자·계약 등록 확인창은 부모 화면 안에서 접근한다. 개별 메뉴가 필요한 경우에만 별도 경로를 등록한다.

## 6. 화면 속성과 업무 상태의 구현 기준

| 영역 | 반드시 모델링할 항목·동작 | 분리해야 할 상태/규칙 |
|---|---|---|
| 리드 | 병원명·상태·소유자, 키맨 성·유형·연락처, 규모·시스템·사업자, 심평원 인입/제외, 컨택제외 사유, 변경 이력 | 단계 선택과 저장을 분리한다. 컨택제외는 정상 순차 단계가 아니다. 좌표 없음은 지도 미표시 경고이며 저장 차단으로 단정하지 않는다. |
| 전환·거래처 | 신규/기존 거래처·연락처·기회 선택, 소유자, 변환 결과; 거래처 상태·주소·ERP 값·병원현황·제품 사용 체크 | CRM 거래처 생성과 ERP 등록/승인을 분리한다. ERP 원천값과 사용자 편집값의 소유권을 구분한다. |

| 기회 | 이름·거래처·마감일·단계·확률, 니즈/제안/협상 속성, 가격 목록·제품·수량·패키지금액 | 경로에서 단계 선택한 값과 저장된 단계를 구분한다. ERP 거래처 승인·연동이 미완료면 수주 성공 저장을 거부한 사례가 있다. |
| 계약 | 기회 제품→패키지명·계약금액 매핑, 제품/상품 금액, 종류·상세·특약, CRM/ERP 계약번호, 등록요청·실패사유 | 계약 생성·ERP 등록요청·ERP 승인·주문가능은 각각 다른 상태다. 승인 후 계약 본문 수정 가능 여부는 별도 결정이 필요하다. |

각 필드는 `observedRequired`와 실제 `requiredRule`을 분리한다. 영상의 별표는 관찰값이며 별표가 없는 필드가 선택이라는 결론은 아니다. 미확인 최대 길이·정규식·숫자 범위·전체 선택지는 기존 코드와 업무 명세를 대조한 뒤 정한다. 그래도 근거가 없으면 동작 가능한 목업 규칙을 `설계 가정`으로 기록하고, 화면·API에 일관되게 적용한다. 이 상태는 해당 화면 구현을 생략하는 근거가 아니다.

### ERP 연동을 전제로 한 화면 흐름

[P0 인터페이스 카탈로그](../../spec/interfaces/P0-07_interface_catalog.md)의 `IF-ERP-001`–`014`를 현재 사용 흐름의 인터페이스 범위로 삼는다. 심평원 인입 `IF-HIRA-001`도 리드·거래처 시드 갱신에 연결한다. 각 인터페이스는 요청·결과의 업무 키, 멱등 키, 원천 시스템, 수신 시각, 재시도, 오류, 감사 로그를 가진다. 목업 ERP 어댑터는 성공을 기본값으로 반환하고 실패·지연·중복·역순 결과를 시험용으로 선택할 수 있게 한다.

| 업무 연결 | 요청 또는 조회 | 목업 ERP 결과가 바꾸는 값 |
|---|---|---|
| 리드·거래처 | 담당자 기준정보, 거래처 등록요청 `IF-ERP-001`–`003` | 담당자 배정, ERP 거래처코드·승인·연동상태. 수주 가능 여부에 반영. |
| 계약 | 계약 등록요청·승인결과 `IF-ERP-004`–`005` | ERP 계약번호, 승인 상태, 주문 가능 상태. |
| 주문 | 품목·단가·재고 `IF-ERP-006`, 주문요청·결과 `IF-ERP-007`–`008` | 주문 가능 품목과 단가, ERP 주문번호, 출고·납품 상태. |
| 수금·매출·계획 | 수금·매출 결과와 변경계획 `IF-ERP-009`–`011` | 실제 수금·매출 행, 미수·원장·명세서, 전송된 계획의 상태. |
| 직출직퇴·반품 | `IF-ERP-012`–`014` | 신청/승인·연동 결과와 반품·교환 관련 목록. |

화면에서 요청 버튼을 누르는 즉시 ERP 승인을 완료한 것으로 처리하지 않는다. 목업은 실제 연동과 같은 요청→수신→업무 상태 반영의 순서를 실행하며 정상 시나리오에서 끝까지 완료할 수 있어야 한다. 실제 ERP의 주소·인증·payload·응답 코드가 제공되면 동일 계약을 쓰는 실제 어댑터로 연결하고 별도의 연결 검증을 수행한다.

## 7. 목업 데이터와 검증 시나리오

목업 데이터는 결정적인 `datasetId`·`schemaVersion`과 안정적인 업무 ID를 사용한다. 한 거래처에 연결된 리드·연락처·기회·계약·수금계획·주문·ERP 결과를 같은 데이터셋에 둔다. 화면을 다시 열거나 새로고침해도 같은 목업 세션에서는 값이 유지되고, 명시적 초기화로 원본 시드가 복원된다. DB/운영 데이터와 저장 공간·API 경로를 분리한다. 목업 실행의 ERP·심평원·메일 응답은 어댑터가 생성하고 `MOCK`를 표시한다. 실제 연동 실행 모드는 별도 환경 설정과 연결 검증을 요구한다.

| 시나리오 | 초기 자료와 조작 | 확인할 결과 |
|---|---|---|
| HQ01 리드 육성 | 신규 리드 생성 → 소유자 배정 → 키맨/병원정보 수정 → 단계 저장·되돌림 | 상세·목록·이력 값 일치, 선택한 단계와 실제 저장 상태 구분. |
| HQ02 리드 전환·ERP 거래처 | 중복 후보 확인 → 신규 거래처·연락처·기회로 전환 → ERP 등록요청·승인결과 수신 | 세 레코드 연결, ERP 거래처코드·승인 상태 반영, 결과 카드에서 상세 이동. 기존 항목 연결은 별도 분기. |
| HQ03 활동·승인 | 활동 계획 → IN → 입력 → OUT → 보고 요청 → 승인 상세 의견·결정 | 보고/승인 상태와 권한별 버튼 변화. 승인 미완료·반려 사례도 재현. |
| HQ04 기회 차단·수주 | ERP 미승인 거래처에서 수주 시도 → ERP 승인결과 수신 → 재시도 | 최초 시도는 저장 거부·입력 보존, 승인 후 실제 단계 변경. 두 사례를 한 사건으로 혼동하지 않음. |
| HQ05 계약·수금 | 수주 제품으로 계약 생성 → 최초 수금계획 → ERP 등록요청·승인결과 수신 → 수금·매출 결과 반영·미수 분할 | ERP 계약번호와 금액 합계, 원본/변경 계획, 요청/승인 상태 구분, 잘못된 합계 거부. |
| HQ06 PC·모바일 주문 | 승인 계약 선택 → ERP 품목·단가·재고 조회 → 품목·수량·배송 → 주문 요청 → ERP 주문·납품 결과 수신 | 같은 주문 ID·총액·입력경로, ERP 주문번호·출고·납품 상태가 상세·관련 목록에 반영. 실패·지연·중복 응답도 재현. |
| HQ07 증빙·분석 | 계약/기간 조건 조회 → 거래명세서·원장·대시보드 | 시드 거래와 합계가 일치하고 조회 기준·빈 결과·파일 결과가 명확함. |
| HQ08 설정 적용 | 본사 등록 화면/항목을 비활성화한 검증용 설정본으로 미리보기·게시 시도 | 메뉴·직접 URL·API·필드·액션 결과가 일치하고 필수 참조를 끊는 게시가 거부됨. 법인 편집 UI 없이 설정 해석을 검증. |

시드에는 정상·미승인·연동실패·중복 후보·수금 미수·재고 없음·주문불가·권한 없음·주소 좌표 없음 사례를 포함한다. 교육영상의 금액과 날짜는 예시 데이터로만 사용하며 서로 다른 계약 사례를 합쳐 만들지 않는다.

## 9. 설계 확정이 필요한 항목

다음은 구현을 멈추기 위한 일반 질문이 아니라, 실제 본사 정책으로 확정하기 전에 분리해 두어야 할 결정이다.

1. 일반 영업·지점장·본부장·영업관리·관리자별 조회·수정·승인 범위와 ERP 원천 필드의 편집 권한.
2. 리드 단계 건너뛰기/역행, 기존 레코드로 전환할 때의 중복·충돌 처리, 전환 실패 시 원자성.
3. 활동보고의 지점장·본부장 순서, 의견 저장·승인완료·반려·재상신의 정확한 상태 전이.
