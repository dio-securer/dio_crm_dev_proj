## 목적과 범위
본사/법인의 메뉴·화면·필드·명칭·권한·승인 흐름을 관리자가 설정하고, 현재 목업 데이터를 이용해 동작을 검증할 수 있도록 한다. 이번 변경은 문서 작성이며 애플리케이션 구현이나 DB 실행은 수행하지 않는다.

사용자 지정 범위:
- 법인·조직·사용자: ADM-01~03, 30
- 권한·보안: ADM-04~06, 13, 28
- 법인별 설정·메뉴·화면: ADM-07~12, 16~18, 34
- 명칭·언어·기준정보: ADM-14~15, 33, 37
- 프로세스·승인·알림: ADM-19~23
- ERP 및 설정 적용: ADM-24~26

“ERP ADM 26까지”는 기존 번호 체계의 ADM-24 ERP 설정, ADM-25 연계 운영, ADM-26 설정 버전·적용까지 포함하는 것으로 해석한다. ADM-26 자체는 ERP 기능 번호가 아니다.

총 31개 ADM 영역을 포함한다. ADM-27 독립 감사관리 화면, 29 첨부 정책, 31 가져오기/내보내기, 32 중복 병합, 35 출력, 36 대시보드, 38 법인 개설 도구는 별도 범위다. 단, 이번 기능의 변경·승인·배포 이력 기록은 필수 내부 기능으로 포함한다.

## 이번 구현의 목표
- DB 없는 브라우저 목업에서도 관리 설정을 저장하고 실제 화면에 적용할 수 있다.
- 같은 국가의 서로 다른 법인도 필드·메뉴·권한·승인 설정이 다르게 동작한다.
- NestJS의 목업 Repository를 사용하는 API 모드에서 서버 검증도 확인한다.
- ERP 요청 → 모의 성공/실패/지연/중복 응답 → 상태 반영/재처리를 재현한다.
- 모든 모의 연계 결과는 화면과 데이터에 MOCK 표시를 유지한다.
- 리드~납품 전체 업무 프로세스 재개발은 이번 단계의 목표가 아니다. 설정 효과를 확인할 거래처/승인 샘플/연계 샘플을 연결한다.

## 범위 결정과 적용 원칙
설정으로 제공할 수 있는 기능은 등록된 화면/액션/연산자 범위로 제한한다. 임의 SQL·JavaScript·외부 URL 실행은 제공하지 않는다. 핵심 금액 계산과 업무 트랜잭션은 개발 코드로 유지한다.

문서 내 예시 법인·결재선·통화·기한·잠금 횟수 등은 목업 검증용이며 실제 현업 확정값이 아니다. 기존 GLOBAL 승인자 미확정 사항을 실제 정책으로 확정하지 않는다.

## 검토 시 유의사항
이 문서는 기존 코드 검토와 사용자 요구사항에 기반한 설계안이다. 영상에서 확인되지 않은 업무 규칙을 확정한 문서가 아니다. 실제 업무 승인자·법인별 필수 항목·ERP payload는 후속 현업 검토에서 확정한다. 본 문서의 모의 시나리오는 그 확인 전에도 설정 기반 동작을 검증할 수 있게 하는 목적이다.

## 추가 요구사항: 영업사원 로그인 MFA 확장 (2026-10-21)
요구 ID: AUTH-MFA-01 · 관련 영역: ADM-28, ADM-03, ADM-04 · 구현 단계: A01/A03/A11.
영업사원 로그인에도 향후 MFA가 필요할 수 있으므로 관리자 전용으로 제한하지 않는다. 실제 인증 수단 도입 시점과 방식은 미정이며 이번에는 정책 모델과 목업 로그인 분기를 준비한다. 아래 내용은 02~06 문서의 MFA 항목을 보완하는 공통 요구사항이다.

| 항목 | 설계 요구 |
|---|---|
| 적용 대상 | 법인·역할별 OFF/OPTIONAL/REQUIRED 정책. 영업사원 역할 포함. 상위 필수 정책을 법인 또는 사용자 설정으로 완화하지 못함 |
| 인증 수단 | MfaProvider 포트로 분리. 실제 TOTP 또는 회사 SSO의 MFA 연계는 후속 선정하며 현재 provider는 DEMO만 사용 |
| 로그인 단계 | 1차 인증 → MFA 등록 필요 또는 챌린지 → 검증 완료 → 업무 세션 발급. MFA 완료 전에는 업무 API 접근 가능한 access/refresh token을 발급하지 않음 |
| 제한 세션 | MFA 중간 세션은 짧은 유효기간과 등록/검증 전용 권한만 부여. 완료·만료·재사용 시 처리 규칙 분리 |
| 사용자 관리 | MFA 등록 상태·등록 수단·마지막 인증 시각 조회, 관리자 초기화 요청과 이력. 비밀값은 조회/로그에 표시하지 않음 |
| 복구 | 단말 분실·변경 시 본인 확인 후 재등록하는 절차를 후속 설계. 관리자 초기화 자체를 인증 성공이나 무기한 MFA 면제로 처리하지 않음 |
| 세션 정책 | MFA 인증 시각/방법을 서버 세션에 기록. 회사 전환 또는 정책 강화 시 현재 인증 수준이 부족하면 추가 인증 요구 |
| 단말 기억 | 기본 비활성. 필요 시 유효기간·회수·법인 정책을 별도 확정하며 localStorage 플래그만으로 인증을 우회하지 않음 |
| 목업 범위 | 미등록/등록/챌린지/성공/실패/만료/초기화 분기 시연. DEMO 표시 유지, 실제 MFA 보안 검증 완료로 보고하지 않음 |

A01에서 인증 세션과 MfaProvider 계약을 분리하고, A03에서 관리자 정책·사용자 상태·영업사원 로그인 분기를 구현한다. 실제 OTP 비밀키 저장, SSO 공급자 연계, 복구 인증 수단은 후속 실제 MFA 구현 범위로 둔다.

A11 추가 인수 조건:
- 영업사원 REQUIRED 정책에서 1차 인증만으로 업무 API를 사용할 수 없다.
- OPTIONAL/OFF/REQUIRED와 상위 필수 정책의 충돌을 검증한다.
- 미등록 사용자 등록 분기, 챌린지 만료·재사용·실패, 초기화 후 재등록을 구분한다.
- 복수 법인 사용자가 MFA 필수 법인으로 전환할 때 인증 수준을 다시 확인한다.
- DEMO 모드가 production에서 활성화되지 않으며, 현재 목업 통과를 실제 MFA 완료로 표현하지 않는다.
