2. 기술 구조 및 개발 원칙

Frontend

React + TypeScript + Vite

업무 Workspace, 활동/GPS, Opportunity/Pipeline, 계약/수금, 주문/이행, Account360, Analytics, Ops Status.

Backend

NestJS + TypeScript

Module/DI/Guard 구조, REST API, Zod Validation, JWT Access/Refresh, explicit business rule validation.

Database / Integration

Microsoft SQL Server + mssql

CRM 내부 DB와 ERP SOR를 분리하고 Integration Adapter / Interface Log로 연결. 운영 ERP 직접 수정 금지.

React Web / PWA
      ↓ REST/JSON + JWT
NestJS API
      ├─ Customer / Activity / Opportunity / Contract / Order / Analytics
      ├─ RBAC / Audit / Approval / Ops
      └─ Integration Framework
              ↓ Adapter / Queue / Retry / Timeout / Circuit Breaker
       ERP / HIRA / File Storage

CRM SQL Server
  └─ bigint IDENTITY + public_id(UUID) + company_id

확정된 Baseline

GPS IN 기본 200m(설정값), User/Organization Master는 ERP, 승인경로는 영업담당자 → 지점장 → 본부장, 승인 요청 시 Snapshot, Lead CONVERTED Terminal, 계약생성 후 Won Opportunity 재오픈 금지, 외부/API 식별자는 UUID.

AI Orchestration 공통 흐름

Orchestrator → Requirement → Domain → Architect → Data/Integration → Backend/Frontend → QA → Review → Human Gate → Merge

Spec에 없는 규칙은 임의 구현하지 않고 SPEC GAP으로 관리.

4. Phase별 상세 개발 단계

Phase 0 — Specification Baseline

APPROVED

두 CRM 교육자료와 오케스트레이션 설계를 Canonical Spec으로 변환하여 AI가 임의 해석하지 않도록 개발 기준을 고정.

P0-07~09

주요 결정: GPS 200m 설정값, ERP User/Org Master, 승인 Snapshot, 상태 역전이 정책, bigint+UUID+company_id.

Phase 1 — Platform Foundation

APPROVED

모든 업무모듈이 공통으로 사용할 인증/권한/감사/연동 기반 구축.

Phase 2 — Customer / Lead / Account

APPROVED

신규 병원 수신부터 영업 Lead 관리, 거래처 전환까지 Customer Domain 구현.

Phase 3 — Sales Activity

APPROVED

현장 영업활동의 계획 → GPS IN → 상담 → OUT → 보고 → 승인 → 직출/직퇴 전 과정을 자체 CRM으로 구현.

P3-04~05

다른 IN_PROGRESS 활동 존재 시 신규 IN 차단. 최종 승인 보고 포함 활동은 수정 차단. ERP DirectWork는 실제 Adapter 전까지 REQUESTING Queue.

Phase 4 — Opportunity / Sales Pipeline

APPROVED

영업기회 생성부터 제안·협상·수주/실주, 제품/패키지, Funnel 분석을 구현.

P4-03~04

P4-05~06

Phase 5 — ERP Account / Contract / Collection

APPROVED

CRM 영업기회를 ERP 거래처/계약/수금 흐름으로 연결하는 Source Baseline 구현.

Phase 6 — Order / Delivery / Sales / Return

APPROVED

8. 다음 실제 실행 순서

DEV/UAT Migration→ ERP/Storage 연동→ Backup/Restore Drill→ UAT/Pilot→ Production Approval→ Cutover→ Hyper-care

Production Go/No-Go 기본조건

Migration 검증, DB Integrity, API Health/Readiness, ERP 핵심 인터페이스, 권한/승인 E2E, Backup/Restore Drill, Pilot Acceptance가 모두 확인되어야 함.

운영 원칙

Production Cutover는 별도 명시적 승인 전 실행하지 않으며, 문제 발생 시 Rollback Runbook과 crm_release_event를 기준으로 변경 이력을 추적.
